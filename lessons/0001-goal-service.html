读懂 GoalService 的两条数据流

完成本课后，你能从一次 create() 追到持久事件和投影，也能解释 Session 恢复后为什么不会擅自自动续行。

领域模型写入线读取线恢复速查表

一、先区分 durable 与 runtime

持久状态

objective、phase、revision、Round 上限与已准入轮数来自 Session 事件，进程重启后可恢复。

运行状态

activation 存在 WeakMap<Session, GoalRuntimeState> 中，只表示当前进程是否获准自动续行。

所以 phase: active 与 activation: armed 是两个判断。前者回答“目标是否仍在推进阶段”，后者回答“这个进程现在能否自动发起下一轮”。

二、沿 create() 走完写入线

  1. resolveCreateGoal() 清理 objective，并解析默认 Round 上限。
  2. prepareMutation() 要求传入 registry 中完全相同的 live Agent，并读取当前投影与 runtime。
  3. 创建新 GoalId、revision 1、phase active 的完整快照。
  4. commitSnapshot() 构造 version 1 的 goal/change 数据。
  5. commit() 调用 session.append()；Session 事件监听器同步更新投影和 activation。
  6. 持久提交成功后才发布 goal/changed，供 driver 等运行中消费者响应。
const goal = ctx.goals.create(agent, {
  objective: '完成配置迁移并验证',
  maxGoalRounds: 8,
})

// 后续更新必须携带精确版本
const paused = ctx.goals.pause(agent, {
  id: goal.id,
  revision: goal.revision,
})

revision 是 compare-and-set 栅栏。若另一调用方先把 revision 1 更新成 2，仍持有 revision 1 的调用会收到 GOAL_STALE_REVISION，不会覆盖新状态。

三、读取线是投影，不是临时缓存

GoalService 启动时向 ctx.sessionProjections 注册 key 为 goal 的 projection unit。它只处理两类事件：

  • goal/change：替换 Goal 完整状态或应用 clear tombstone。
  • 来源为 kind: goal 的 user/message：把 roundsStarted 推进到下一轮。

ctx.goals.get(agent) 读取当前投影，再附上 runtime activation。普通 inbox 变化、assistant 消息和工具结果不会改变 Goal 投影。

四、恢复时为什么 fail closed

fold.ts 会重新验证每条 Goal 事件：字段必须精确、revision 必须连续、phase 转换必须合法、Goal ID 不能复用、Round 必须连续且属于当前 revision。发现第一条坏记录后，投影保留最后一个有效客户端视图和 failure；Host 的 Goal 读写则拒绝继续。

独立的 invariant companion 更早介入：它在 session/event 发布前用另一份 fold 检查候选事件，非法事件会在提交之前被拒绝。这是一道写入期防线；projection failure 是读取与恢复期防线。
